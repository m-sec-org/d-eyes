# 0.1 Agent CLI wiring & telemetry review

## Entry points & CLI surface
- `agent/d-eyes.go` and `agent/cmd/agent/main.go` each bootstrap `agent/internal/agent.Runtime` and exit via `os.Exit`, so there is no standalone `cmd/d-eyes` tree in this repo. (`agent/d-eyes.go`, `agent/cmd/agent/main.go`)
- `Runtime.Run` injects `remote`/`collect` commands, shows ASCII logo, initialises logging, then defers to the shared `internal.App` CLI instance (`agent/internal/agent/runtime.go:32-115`).
- `internal.App` is composed once at package init time: it loads config in `App.Before`, registers global flags (`--profile`, `--json`, `--quiet`, etc.), and wires each sub-command by calling `newTaskCommand` with a `TaskRunner` from `internal.RunnerFactory` (`agent/internal/app.go:33-232`, `agent/internal/app.go:344-523`).
- `newTaskCommand` builds a `tasks.TaskRequest` from CLI args, copies the resolved config, forces quiet-mode globally via `internal.SetQuietMode`, and calls `tasks.Execute` with the resolved runner (`agent/internal/app.go:470-523`).
- Remote CLI (`d-eyes remote`) is appended by `ensureRemoteCommand`; it defers to `agent/internal/agent.RunRemote` which spins up the daemon runner (`agent/internal/agent/runtime.go:101-137`).

## Runner lifecycle & telemetry hooks
1. **TaskRequest/TaskResult plumbing**
   - `TaskRunner` implementations live under `agent/internal/tasks`. Each runner accepts `TaskRequest`, reads specialised flags, and returns `TaskResult` populated with `Outputs`, `Risks`, `Notes`, and optional `Metadata` (e.g., inventory caches, BAS stats). (`agent/internal/tasks/types.go`, runner files)
   - Requests automatically fill defaults (profile, timeout, metadata maps) in `TaskRequest.ApplyDefaults`. Metadata is also used to pass sandbox approvals and flag derived info to remote executors (`agent/internal/tasks/types.go:88-169`).

2. **Execution wrapper**
   - `tasks.Execute` / `ExecuteWithResult` are the only callers of runners from CLI and remote paths. They measure runtime, aggregate policy errors, print JSON if `--json` is set, emit notices, and delegate to `reporting.Manager.PrintSummary` unless `--quiet` is active (`agent/internal/tasks/execute.go:20-118`).
   - `telemetry.NewTaskResourceTracker` is created before runner invocation; `AppendTaskResourceMetadata` encodes CPU/memory/IO/net deltas under `telemetry.task.*` keys and `telemetry.task_resources`. This happens for every runner invocation regardless of CLI vs remote (`agent/internal/tasks/execute.go:36-46`, `agent/internal/telemetry/taskmetrics.go`).
   - `tasks.ToExecutionResult` copies `TaskResult.Metadata` plus telemetry fields into `model.ExecutionResult`, which remote mode later uploads (`agent/internal/tasks/execute.go:120-175`). No additional progress timestamps or event logs are persisted today.

3. **Remote daemon integration**
   - The remote runner (`agent/internal/agent/daemon.go`) resolves the same runners via `internal.TaskRunnerByName`, always enforces quiet mode / JSON summary off, and uses `tasks.ExecuteWithResult` to get `ExecutionResult`. It merges `telemetry.CollectExecutionMetadata(ctx)` outputs before uploading results (`agent/internal/agent/daemon.go:797-904`).
   - `telemetry.CollectExecutionMetadata` is currently a no-op because the default collector returns `nil` unless another component overrides it, so no extra process-tree/network snapshots are captured out of the box (`agent/internal/telemetry/telemetry.go:118-175, 247-266`).
   - `telemetry.StartSystemSampler` runs continuously in remote mode to feed CPU/memory/IO stats into heartbeats, but CLI-only runs do not start the sampler (`agent/internal/agent/daemon.go:707`, `agent/internal/telemetry/telemetry.go:192-227`).

4. **Reporting & quiet-mode handling**
   - `reporting.Manager` owns artifact directories and prints a one-shot textual summary to stdout via `PrintSummary`. There is no incremental progress UI beyond this final summary (`agent/pkg/reporting/manager.go:1-99`).
   - `internal.SetQuietMode` tracks `--quiet` globally so `Runtime.Run` can suppress the closing "Thank you" banner (`agent/internal/agent/runtime.go:62-91`, `agent/internal/config_runtime.go:38-70`).

## Command-specific progress / telemetry mapping
| Command | Runner wiring | Progress hooks today | Telemetry / metadata today |
|---------|---------------|----------------------|----------------------------|
| `respond` | `respondRunner` sequences profile modules (`runHostSummary`, `runNetworkAnalysis`, `runFileScan`, etc.). (`agent/internal/tasks/respond.go`) | No `progress.Manager` usage; modules run sequentially and only append notes/errors. CLI output = final summary only. | Metadata is cloned from `TaskRequest.Metadata` (which is empty unless caller sets it). No additional telemetry beyond `telemetry.task.*` from `Execute`. |
| `audit` | `auditRunner` composes `baselineRunner`, `runHostSummary`, `runUserInspection`. (`agent/internal/tasks/audit.go`) | No progress instrumentation; sub-runners run serially. Baseline portion inherits behaviour described below. | Metadata limited to baseline output + JSON summary artifact. |
| `inventory` | `inventoryRunner` iterates targets, calling `defaultInventoryExecutor.ScanTarget` which wraps `assets.AssetScanner`. (`agent/internal/tasks/inventory.go`) | Each scan instantiates `progress.NewManager(progress.NullReporter{}, ...)`, so `AssetScanner` stages (discover hosts, port scans, service detect) are **not surfaced** to CLI. The `assets` package itself supports rich console progress if it receives a real reporter (see `agent/internal/assets/runner.go:100-152`, `agent/internal/progress/reporter.go`). | `TaskResult.Metadata` records profile, targets, cache hits/misses, and summary writer adds risk stats. Telemetry is limited to these summary counters plus `telemetry.task.*`. |
| `supplychain` | `supplyChainRunner` is pure Go (manifest scanning / pip capture) without sub-runners. (`agent/internal/tasks/supplychain.go`) | No progress or stage reporting; long-running scans only emit final summary/notes. | Metadata tracks cache statistics, manifest reuse ratios, and report format. |
| `baseline` | `baselineRunner` calls `benchmarkexec.Execute`. The benchmark scanner wires `progress.NewManager(progress.NullReporter{}, ...)` around the engine, meaning benchmark stages (`StageBenchmark`, `StageBenchmarkChecks`) are collected but never printed. (`agent/internal/tasks/baseline.go`, `agent/internal/benchmarkexec/runner.go`) | Same: no CLI output. `progress.Manager` only feeds checkers internally. | Metadata stores scope, profile, format, config path, risk totals. |
| `BAS` | `basRunner` executes scenario steps (possibly inside sandbox) and records success/failure counts. (`agent/internal/tasks/bas.go`) | No incremental progress to stdout; sandbox + step telemetry is only stored after each scenario run. | Rich metadata: scenario descriptors plus encoded `telemetry.bas_steps` and `telemetry.sandbox_stats` payloads via `telemetry.EncodeBASteps/EncodeSandboxStats`. |
| `collect` | Separate CLI command (`agent/internal/agent/collect_command.go`) building `collector.Service`. Each collector streams `SystemEvent` structs through the configured handler/output. | No formal progress; CLI prints startup/shutdown notices and then raw JSON events. Collectors themselves implement `CollectorStatus` but there is no periodic status display besides manual `service.Status()` call during startup. | Event metadata automatically gets `collector` / `collector_kind`; additional telemetry depends on each collector's payload. Service does not persist execution metadata. |
| Remote auto-respond | Remote runner reuses `respondRunner` asynchronously when detections trigger automation (`agent/internal/agent/daemon.go:421-490`). | No CLI visibility. Execution metadata stored in the remote payload only contains `telemetry.task.*` and detection context inserted into `TaskRequest.Metadata`. |

## Key observations & implications for debug mode
- All core commands route through `tasks.Execute`, so instrumentation for progress/debug events can be centralised there (e.g., hooking into `TaskRequest.Manager`, `TaskResult.Metadata`, or extending the runner interface).
- `progress.Manager` already tracks meaningful stages inside inventory and baseline flows, but the CLI intentionally swaps in `progress.NullReporter`, so surfacing these requires only wiring a reporter tied to new debug output sinks.
- Respond/audit/BAS/supplychain runners lack any stage callbacks; adding debug emissions will require either shared helper hooks or per-runner instrumentation.
- Remote execution already persists `ExecutionResult.metadata` to the server; any debug/progress timeline we capture locally can be propagated to remote consumers by appending structured strings to this metadata map before `tasks.ToExecutionResult` runs.
- `telemetry.CollectExecutionMetadata` is currently unused in production (default collector returns nil). If debug mode needs richer context (process tree, network lists), supplying an actual collector implementation—or replacing it only when debug mode is on—will prevent overhead for normal runs.
- The `collect` command bypasses `tasks.Execute`, so any debug/progress story there must hook into `collector.Service` directly (e.g., periodic status snapshots or handler-side telemetry).
