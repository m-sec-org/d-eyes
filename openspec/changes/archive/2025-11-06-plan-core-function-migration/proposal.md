## Why
- `docs/design-next.md:254-270` 明确阶段二需要把现有 CLI 核心能力迁移到分布式 Agent-Server 架构，但当前仅完成阶段一基础设施交付（参见 `openspec/changes/plan-agent-server-foundation/tasks.md`），缺乏可执行的阶段二实施路径。
- 现有功能仍集中在 CLI 单体代码中，例如应急响应 `agent/internal/detect`、基线检查 `agent/internal/tasks/baseline`, 资产梳理 `agent/internal/assets` 与供应链能力 `agent/internal/sbom`；Server 侧也尚未提供统一的结果聚合与报告链路（`server/internal/store`、`server/internal/api` 均只覆盖基础能力）。
- 若不尽快规划模块迁移节奏与交付边界，将导致 Server 与 Agent 的功能不对齐、任务编排无法落地、BAS 模块无法与其他能力协同，同时也会阻塞 Web 管控面的完善。

## What Changes
- 以阶段二 4 个月周期为边界，拆解成四个里程碑（C-F），分别覆盖迁移框架拓展、核心模块分批迁移、BAS 基础架构落地、以及 Web/报告能力完善，确保每个里程碑都可验收。
- 定义跨模块统一的任务/结果契约（gRPC proto、任务模型、结果序列化方案），并升级 Server 任务调度、队列与数据存储，使其具备模块级路由、并发控制和可观测性。
- 为应急响应、基线检查、资产探测、供应链分析四类能力制定“迁移→遥测→回归校验”流程，要求在 Agent 中提供远程执行入口、缓存策略和失败回退，同时在 Server 端新增结果聚合、索引与报告生成。
- 设计并交付 BAS 模块基础框架：任务模型、隔离策略（gVisor 沙箱）、最小攻击场景编排、以及安全护栏；并将相关指标纳入调度与监控体系。
- 完成 Web 管控面的任务配置、执行监控、结果浏览与报告导出改造，使分布式链路真正可视化，满足阶段二“任务配置与监控功能完善”的目标。

## Impact
- 代码层面需要大规模修改 Agent 和 Server：扩展 `server/proto` 与 `server/internal/*`（scheduler、queue、store、api），在 Agent 端重构 `internal/tasks` 以支持远程执行、并实现模块化插件打包与配置下发。
- 数据层面需要引入结果聚合与索引模型（可能新增 PostgreSQL schema、Elastic 索引），以及任务/结果状态机，影响现有数据库迁移与运维部署脚本。
- 测试策略将升级为模块级端到端矩阵：需覆盖 CLI 兼容模式与 Agent-Server 模式两条链路，对性能（并发调度、结果写入）、安全性（BAS 沙箱）与可靠性（断点续跑、数据补写）进行专项评估。
- 文档需要同步更新：开发者指南、插件规范、运维部署、以及 Web 使用手册必须覆盖新的任务类型和操作流程。

## 里程碑 E 设计（BAS 子任务沙箱化方案）

### 目标
- 在不影响现有 Agent CLI 功能的前提下，为 BAS 任务引入按需沙箱化执行机制，确保攻击模拟具备隔离、安全审计与资源控制能力。
- 形成可迭代的 BAS 流程：场景描述、沙箱配置、执行回传、指标与审计接口，支撑后续场景库扩展。

### 方案概述
1. **混合执行模型**
   - BAS 任务拆分为“宿主调度 + 沙箱子任务”两阶段：宿主 Agent 负责解析场景、准备依赖、管理数据通道；危险步骤在 gVisor/容器沙箱中执行，执行完成后通过共享挂载或管道回传结果。
   - 非 BAS 模块（Respond/Baseline/Inventory/SupplyChain 等）继续沿用宿主执行路径，不引入沙箱开销。
2. **沙箱控制平面**
   - Agent 侧新增 `sandbox` 子模块，封装 gVisor runtime 调度、镜像管理、资源限制、共享目录、安全审计（命令白名单、超时、带宽等）。
   - Server 调度层扩展 BAS 并发阈值（`scheduler.bas_max_concurrency`），调度器追踪 `task_type` 与场景信息；结果模型新增 `scenario_id/name` 等字段，用于后续攻击链展示。
   - 配置开关：在 Agent 配置 (`sandbox.enabled`, `sandbox.runtime`, `sandbox.shared_paths`) 中控制沙箱能力，禁用时可降级为“仅允许低风险步骤”或拒绝执行。
3. **数据与结果通道**
   - 约定沙箱共享目录（只读输入、只写输出），用于传递脚本、payload、日志；宿主 Agent 汇总结果并转为统一 `ExecutionResult`。
   - Server 后续里程碑提供 BAS 专属报告接口，展示步骤、证据、执行链路。
4. **安全与审计**
   - 每个 BAS 场景定义安全参数：白名单命令、最大执行时长、网络策略、审批状态等。
  - Server 记录审计日志（创建者、场景、步骤、资源消耗），并暴露 Prometheus 指标：沙箱实例数、失败原因、超时次数等。

### 里程碑拆解
1. **E1：任务模型与调度扩展**（已完成）  
   - 新增 BAS 任务类型、并发阈值、结果字段（`scenario_id/name`），完善调度器与存储层。
2. **E2：Agent 沙箱执行框架**  
   - 集成 gVisor/容器 runtime，完成最小可用沙箱运行器：启动/停止、挂载目录、日志收集、错误回传；提供配置开关与回退策略。
3. **E3：场景描述与执行流水线**  
   - 定义 BAS 场景 DSL（JSON/YAML），支持阶段拆分、安全控制参数；Server 解析场景、派发子步骤，Agent 在沙箱中执行并回传；交付最小场景库及回归测试。
4. **E4：可视化与审计**  
   - REST/前端接口展示场景、步骤、证据；扩充监控指标与审计日志，完善文档、运维指南与审批流程。

### 风险与缓解
- **环境依赖**：需确认目标系统支持 gVisor；提供检测脚本与安装文档，允许关闭沙箱模式。
- **性能开销**：沙箱启动可能耗时，可采用预热池、批量执行策略；非 BAS 模块不受影响。
- **资源消耗**：通过 `bas_max_concurrency`、资源限额和配额配置控制；调度层监控并发。
- **数据隔离**：定义共享目录协议，确保跨任务隔离；对输出进行清洗与校验。

### 测试策略
- 单元测试：沙箱配置解析、运行器接口、调度并发与回退逻辑。
- 集成测试：使用 fake/gVisor stub 验证 BAS 任务从 Server → Agent → 沙箱 → 结果回传全链路，同时确保其他模块既有测试通过。
- 安全/性能：后续阶段补充压力测试、资源限额与审批流程验证。

## Open Questions
- CLI 与 Agent 模式是否在阶段二仍需保持双模式可用？若需要并行支持，必须明确回退策略和配置切换方式。
- Server 端结果存储是否全部进入 PostgreSQL，还是结合 Elasticsearch 做全文索引？需要在设计阶段确认数据分层与成本。
- BAS 模块的最小可交付范围如何界定（例如只覆盖侦察与初始访问，还是包含权限提升/横向移动）？需与安全团队达成共识。
- Web 管控面是否引入实时推送（WebSocket）用于任务进度刷新？如需实现，需评估与现有 API/权限模型的兼容性。
