# Frontend ↔ Server 对齐矩阵（0.1 盘点产出）

> change-id: `align-frontend-server-core-capabilities`  
> 本文聚焦前端 `tasks/create`、`task detail`、`agents/labels`、`reports` 四块与 Server 的接口/数据对齐现状，并标注对应 Specs 覆盖与缺口，作为 0.2 的口径收敛输入。
> **决策记录（生产鉴权/Headers 注入）**：生产形态由 **网关/反向代理** 统一注入 `X-API-Key` 与 `X-User`/`X-User-Role`（敏感接口再叠加 `X-MFA-Code`）；浏览器侧不直接持有/发送 API Key，`Authorization: Bearer` 仅用于网关侧登录态/SSO（Server 本身不解析）。

## A. 现状总览（关键结论）

- **Task Catalog 已接入（类型/Profiles）**：前端已调用 `GET /api/v1/task-types` + `GET /api/v1/task-profiles` 驱动创建表单，但缺少对 `constraints` 的 UI guardrails（尤其 memscan 的 `pid/all` 互斥）。
- **调度合同缺口（required_capabilities）**：前端创建任务未默认写入 `metadata.required_capabilities`，导致 scheduler capability filtering 不稳定（可能把任务 lease 给不支持该任务的 Agent）。
- **Report/read 缺口（audit/detect）**：Server 已提供 `GET /api/v1/tasks/{id}/audit/report` 与 `GET /api/v1/tasks/{id}/detect/report`，但前端未消费；当前主要依赖 `task.last_run.summary` 的粗粒度展示。
- **labels 权威认知缺口**：前端提供 Agent labels 编辑，但缺少“Server 侧编辑会被 Agent 下次 Register 覆盖”的提示，容易误导运维用 labels 当控制信号（例如误以为改 `allow_memscan` 就能启用 memscan）。

## B. 跨域注意事项（会影响所有 API 调用）

### B.1 鉴权/身份 Header 口径不一致（高风险）

- Frontend：`frontend/src/services/http.ts` 仅注入 `Authorization: Bearer <token>`。
- Server：`server/internal/api/router.go` 使用 `X-API-Key` + `X-User`/`X-User-Role` 作为 principal/RBAC 来源（未实现 `/auth/login`）。
- 影响：若无额外网关/反向代理注入 Header，控制台直连 Server 将普遍 401/403（例如 `PATCH /api/v1/agents/:id/labels` 需要 `agents.update` 权限）。
- 决策：生产形态由网关/反向代理注入 `X-API-Key`/principal Headers；控制台不直连 Server（不在浏览器侧配置 `X-API-Key`），避免泄露 API Key 与审计失真。

## D. 0.2 需要收敛的口径（建议）

1) **required_capabilities 默认值**：UI 端“永远注入” vs Server 端“基于 catalog 注入兜底”的优先级与兼容性策略。  
2) **memscan UX**：审批字段（必填键与文案）、Windows-only + `allow_memscan="true"` gating 提示、以及 evidence/minidump 的二次确认与默认关闭。  
3) **outputs 语义**：输出为 Agent 本地路径时，“下载”应替换为“复制路径/提示需集中回收能力”；是否隐藏下载按钮。  
4) **鉴权方案（已决策）**：生产由网关/反向代理注入 `X-API-Key` + principal headers；本地联调可通过 dev-proxy 注入同样的 headers（或临时关闭 `security.api_keys`）。
